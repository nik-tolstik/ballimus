## Issue policy

Every non-trivial implementation task starts with a Linear issue in the `FBOT` team and Ballimus project. Do not start implementation before the issue exists and is ready to be worked on.

An isolated typo, formatting-only edit, or obvious CI maintenance change may be made without a separate issue. If the scope is uncertain, create an issue.

Each issue has one current owner and one current status. When an agent has a Linear identity, it assigns the issue to itself before starting. Do not assign another person without their agreement.

## Statuses

| Status | Meaning |
| --- | --- |
| `Backlog` | An idea or request that still needs refinement or prioritisation. |
| `Todo` | Defined work that is ready for an executor to pick up. |
| `In Progress` | An executor has started work. Keep this status while implementation, review, or follow-up work remains. |
| `Done` | The pull request is merged, CI is green, and the change is present in `main`. |

Only move an issue to `Done` after all three conditions are met. A merged commit alone is not enough if the relevant CI has not passed.

## Workflow for contributors and coding agents

Before implementation, the contributor or agent must:

1. Read the issue description, status, assignee, and dependencies in Linear.
2. Check that another executor is not already actively working on it.
3. Move the issue to `In Progress` and assign it to itself when possible.
4. Create a dedicated branch and worktree.

During implementation:

- Keep the issue in `In Progress` while its pull request is open, under review, or blocked.
- Record blockers and dependencies in Linear instead of silently leaving work unfinished.
- When work pauses, add a comment that states what was completed, what is blocking progress, and what the next executor needs to do.
- Add the pull request link to the Linear issue so the delivery history remains discoverable.

After implementation:

1. Update the issue description when the delivered scope differs materially from the original scope.
2. Confirm that the pull request is merged, CI is green, and the change is in `main`.
3. Remove the task worktree and its local branch unless the owner explicitly asks to keep them.
4. Move the issue to `Done`.

## Git and Linear conventions

Use the branch name generated by Linear when it is available. Otherwise, use the issue identifier in the branch name:

```text
fbot-123-add-auth
```

Prefix commits with the Linear issue identifier:

```text
FBOT-123 Add Google authentication
```

Mention the issue identifier in the pull request title or description. This lets GitHub and Linear link the implementation to its delivery record.

## Definition of Done

An issue is done only when all of the following are true:

- The requested implementation is complete.
- Relevant checks and tests have passed.
- The pull request is merged into `main`.
- The relevant CI is green.
- The Linear issue contains a link to the pull request.
- The Linear issue is moved to `Done`.
